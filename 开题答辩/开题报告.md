## 一、选题背景与意义

### 1.1 行业背景

随着大语言模型（Large Language Model, LLM）技术的快速成熟，人工智能辅助内容创作已成为数字内容产业的重要方向。网文写作、自媒体运营、公文撰写等场景对长文产出效率与文字质量提出了越来越高的要求，AI 写作辅助由此从"可选功能"逐步演变为创作者的基础工具。与此同时，开源大模型（如 Qwen、Llama 系列）与本地推理工具（如 Ollama）的普及，使"模型在本机、数据不出本机"的私有化推理具备现实可行性，为桌面端离线智能写作提供了技术前提。

在工程实现层面，Java 生态的 AI 集成框架正在快速成型：Spring 官方推出的 **Spring AI** 在 1.0.0 GA 版本中统一了对话模型抽象（ChatClient）、流式输出（Flux）与工具调用等能力，使 Java 后端能够以较低成本接入大模型。然而，将本机后端、桌面应用与本地/在线模型三者有机结合并交付为 Personal Computer（PC）桌面产品的完整工程实践，目前仍缺少公开可参考的范例。

### 1.2 现实痛点

1. **隐私与离线诉求未满足**：主流在线 AI 写作工具（如各类云端 SaaS）普遍要求联网并上传正文内容，用户的创作草稿、商业构思等敏感文本被传输至第三方服务器，隐私风险突出；一旦断网则核心能力不可用。
2. **重"生成"而轻"写作体验"**：现有 AI 写作产品多以"一键成文"为卖点，忽视写作工具本体的编辑体验、防丢稿、版本留存与多格式导出，长文创作者真正需要的"写得顺手"未被很好解决。
3. **本地模型使用门槛与认知偏差**：用户容易混淆"下载预训练模型"与"训练模型"，面对命令行工具望而却步，缺少一个把本地模型能力"产品化""可诊断化"的桌面应用。
4. **Java / Spring 栈在桌面 AI 写作中的工程空白**：桌面端如何编排本机 Java 后端进程、如何在本机 HTTP 接口上做纵深防御、如何在单文件数据库上保证并发写一致性，这些问题缺少系统性工程参考。

### 1.3 研究意义与应用价值

1. **应用价值**：面向个人创作者提供一款"写作体验优先、AI 随手可用、隐私可离线"的 Windows 桌面工具；支持"本地 Ollama 离线推理"与"用户自备第三方 API 密钥联网使用"双模式，兼顾隐私与开箱即用。
2. **技术价值**：以 Spring Boot + Spring AI 为后端核心，完整实践桌面进程编排、SSE 流式输出与资源释放、本机接口纵深防御、SQLite 并发与 WAL 一致性、富文本位置映射等工程难点，形成可复用的工程经验。
3. **方法论价值**：体现"以工具本体为主、AI 为赋能"的产品取舍方法，探索在有限周期与业余工时约束下，通过里程碑驱动的增量交付保障本科毕设质量。

## 二、国内外研究现状

### 2.1 AI 写作辅助工具

国外方面，Notion AI、Jasper、Grammarly 等产品将 AI 能力嵌入文档与写作流程，提供续写、改写、摘要与风格调整等功能，但其形态以云端 SaaS 为主，依赖联网、按订阅计费，正文数据需上传云端。国内方面，秘塔写作猫、语雀"AI 助手"、各类自媒体辅助平台同样以网页端为主，普遍强调在线创作与协同，隐私本地化能力较弱。

### 2.2 开源本地大模型与 Ollama

Meta 的 Llama、阿里云的通义千问（Qwen）等开源权重模型使高质量中文推理可在消费级硬件上运行；Ollama 以简洁的本地 HTTP 服务封装了模型下载与推理，显著降低了本地部署门槛。相关研究多聚焦模型压缩、量化与推理加速，而"如何将本地模型能力嵌入桌面写作工具并获得稳定的产品体验"这一工程问题，讨论仍然有限。

### 2.3 桌面富文本编辑器生态

Electron 使 Web 技术栈能够构建跨平台桌面应用（如 VS Code、Obsidian），其渲染进程可复用成熟的 Web 编辑器内核。ProseMirror 及其上层封装 TipTap 提供了结构化文档模型、撤销 / 重做、输入规则与稳定的位置映射（position mapping）能力，已成为现代富文本编辑器的主流方案。现有实践证明了"Electron + 现代编辑器内核"构建本地优先写作工具的可行性，但与之配套的本机 AI 后端集成实践较少。

### 2.4 Java AI 框架生态（Spring AI）

Spring AI 1.0.0 GA 提供统一的模型抽象、流式响应与提示词模板能力，并兼容 Ollama 与 OpenAI 兼容接口。相关研究与实践多集中于服务端（Web / 微服务）场景，围绕"容器化部署、云端推理"展开；对于"作为桌面进程被编排、只在本机回环地址监听、需要进程生命周期治理"的桌面内嵌后端形态，缺少系统化的工程范式。

### 2.5 现有方案的不足与空白

综合来看，现有方案存在以下不足与研究空白：

1. **隐私与离线能力不足**：多数工具强联网、数据上云，离线（尤其完全离线）写作能力薄弱。
2. **工具本体与 AI 融合不均衡**：偏重 AI 生成，弱化编辑体验、防丢稿、版本与导出等写作核心。
3. **工程范式缺失**：缺少 Java / Spring 栈在"桌面应用 + 本机后端 + 本地 / 在线双模式模型"场景下，覆盖进程编排、本机安全、单文件数据库并发与打包交付的端到端实践。
4. **可诊断性不足**：本地模型环境的可用性诊断（是否安装、是否就绪、模型是否缺失）缺乏标准化、可解释的状态模型。

本课题正是针对上述空白，围绕"桌面码字工具 + AI 赋能 + 双模式模型接入"展开设计与实现。

## 三、研究内容与目标

### 3.1 总体目标

设计并实现一款面向个人创作者的 Windows x64 桌面智能写作助手，以桌面码字工具为本体、AI 为写作赋能，通过后端 **Spring Boot 3.5.3 + Spring AI 1.0.0** 统一接入本地 Ollama 与用户自备第三方 API 两种模式，在 8 周（56 天）周期内交付可安装、可运行、可演示的 MVP（Minimum Viable Product，最小可行产品）成品。

### 3.2 分模块研究内容

1. **写作核心（工具本体）**

   - 基于 **TipTap（ProseMirror 内核）** 的富文本编辑器：基础排版、Markdown 快捷输入、正文以 HTML 持久化、以纯文本投影供 AI 与统计使用。

   - 文档管理：新建 / 重命名 / 分组 / 搜索 / 删除，按更新时间排序与按文体过滤。

   - 防丢稿：正文输入防抖实时自动缓存，崩溃 / 重启后恢复草稿。

   - 版本留存：手动存版与会话结束自动存版、双版本差异对比、一键回滚（回滚作为新版本追加）。

   - 多格式导出：txt / md / word（Apache POI XWPF 结构化基础排版），按文体给出默认格式。

   - 写作舒适辅助：护眼暗色主题、悬浮字数统计（当前文档总字数 / 选中字数）。
2. **AI 赋能（保留项）**

   - AI 续写：光标处依据上文语境流式续写，结果流式插入并可撤销。

   - 选中文字快捷处理：扩写 / 精简 / 换风格 / 调篇幅，原地替换可撤销。

   - 大纲与灵感：由零散关键点生成结构化大纲、按主题给出标题 / 开头 / 情节建议。

   - 素材收藏与插入：选中文本收藏为素材，按文体归档并可插入正文。

   - 全文自检：规则引擎（词级）为主、LLM 语义级为辅，问题标红 + 悬浮替换。

   - 文体模板：网文 / 自媒体 / 公文三套系统提示词一键切换。
3. **模型接入与配置**

   - ModelRouter 双模式：LOCAL（本机 Ollama）与 USER\_PROVIDED\_API（用户自备 API 密钥）。

   - 本地模型健康检测：收敛为 UNAVAILABLE / MODEL\_MISSING / READY 三状态。

   - 模型参数配置：创意程度（temperature）、单次生成字数（maxTokens）与双预设保存。
4. **桌面工程与交付**

   - Electron 主进程对后端 Java 进程的生命周期编排、启动遮罩、崩溃自愈与优雅停机。

   - 本机接口纵深防御（X-Local-Token、Host 校验、CORS 白名单）。

   - SQLite 并发与事务约束、WAL 管理。

   - 以 jlink 裁剪 JRE 随包分发的 Windows x64 交付与打包后冒烟测试。

## 四、拟解决的关键问题

本课题的技术难点集中在"桌面应用—本机后端—本地/在线模型"三者的协同与治理上，拟重点解决以下关键问题：

**关键问题 1：桌面端后端进程的生命周期编排与崩溃自愈。**
后端为随桌面应用启动的本机 Java 进程，若不由主进程统一编排，极易出现"关窗后 Java 残留、8080 端口被占用、二次启动失败"。拟采用主进程 `spawn(java, { shell:false })` 直接拉起使 java 成为直接子进程，辅以 `tree-kill`（Windows 等价 `taskkill /T /F`）兜底杀整棵进程树；配合启动遮罩健康轮询、`exit/close` 崩溃自愈重启、JVM `ShutdownHook` 与仅回环可访问的 shutdown 端点实现优雅停机，并回收上次残留端口。

**关键问题 2：SQLite 单写并发与"事务内禁 AI 调用"的一致性保障。**
SQLite 为单文件嵌入式数据库，多连接写极易触发 `database locked`。拟以 Hikari `maximum-pool-size: 1` 约束单写，在连接初始化统一设置 `journal_mode=WAL / synchronous=NORMAL / busy_timeout=5000 / foreign_keys=ON`，并确立"事务内禁止包裹网络 IO 与 AI 调用、禁止长事务长读"的红线，辅以 `wal_checkpoint(TRUNCATE)` 防止 WAL 膨胀、单进程独占保证库文件一致性。

**关键问题 3：回环地址下本机 HTTP 接口的纵深防御。**
`localhost` 并非安全边界，恶意网页可通过 `fetch` 或 DNS rebinding 访问本机服务。拟采用后端启动生成一次性随机令牌 `X-Local-Token` 并写入应用数据目录本地文件、由主进程读取经 preload 注入渲染进程，**令牌永不经过 HTTP 传输**；业务接口强制校验该请求头（不匹配返回 401），Host 头仅允许 `localhost / 127.0.0.1`，CORS 禁用 `*`。

**关键问题 4：SSE 流式输出的资源释放与断连保活。**
流式生成若不能及时释放，会导致模型后台空跑与线程 / 网络资源泄漏。拟以 **SseEmitter**（不引入 WebFlux）承载 Spring AI 返回的 Flux 并持有 `Disposable`，以约 15 s 心跳保活、写失败即判定客户端断开并 `dispose()`，配合 WebClient 显式连接 / 读超时与前端 `AbortController` 取消；SSE 事件严格限定为 token / error / complete 白名单。

**关键问题 5：纯文本偏移与富文本位置映射驱动的自检标注。**
全文自检返回的问题偏移以纯文本投影（UTF-16 code unit）为基准，需映射到 ProseMirror 文档位置才能精确标红与替换。拟基于 TipTap / ProseMirror 成熟的位置映射能力完成"纯文本 offset ↔ ProseMirror position"转换，替换经编辑器事务执行以进入撤销栈，替换后重取文本重建映射；并采用"仅手动触发一次、用户编辑即清空标记"的策略，规避实时增量标红的高频重算开销。

**关键问题 6：打包后资源与数据路径解析及零依赖交付。**
开发环境跑通、打包成 exe 后路径全变是典型陷阱。拟由主进程以 `--writer.data-dir=<userData>/data` 注入数据目录，Java 侧按"启动参数 → 环境变量 → `user.home` 兜底"解析，库文件、`agent.yml` 与令牌文件全部落于该目录、禁止写死相对路径；并以 jlink 裁剪 JRE（约 50–90 MB）随 `extraResources` 分发，使用户无需预装 JDK21。

## 五、技术路线与实施方案

### 5.1 技术选型与对照

| 层次    | 选型                                                                    | 备选 / 对照            | 选型理由                                            |

| 桌面壳   | Electron ≥28 + Vite + Vue3 + TypeScript + Element Plus                | 纯 Web 应用 / Qt      | 复用 Web 生态与成熟组件，跨平台打包便利，桌面本地能力强                  |
| 编辑器内核 | TipTap（ProseMirror 内核）                                                | 自研 contenteditable | 文档模型、撤销重做、位置映射成熟稳定，避免重复造轮子                      |
| 后端框架  | Spring Boot 3.5.3 + JDK21                                             | 纯 Node.js 后端       | 选题核心；Spring AI 生态完善，分层与工程规范成熟                   |

| 流式输出  | SseEmitter（spring-boot-starter-web）                                   | WebFlux            | 满足 SSE 需求而不引入响应式全栈改造                            |
| 持久化   | SQLite（sqlite-jdbc）+ MyBatis-Plus                                     | MySQL / Redis      | 单机单用户、数据即本地文件、零服务依赖；无需 Redis                    |
| 文档导出  | Apache POI（XWPF）                                                      | 第三方转换库             | 直接生成 .docx，结构化基础排版即可                            |
| 打包交付  | electron-builder + jlink 裁剪 JRE                                       | 依赖用户预装 JDK         | 零依赖交付，安装即用                                      |
| 进程管理  | 主进程 spawn + tree-kill                                                 | shell 包装启动         | 保证子进程可被可靠回收，避免端口残留                              |

### 5.2 系统分层架构

系统分为五层：

1. **渲染进程（Renderer）**：Vue3 + Element Plus 构建界面，TipTap 承载正文编辑；通过 fetch + ReadableStream 处理 SSE；所有业务请求携带 `X-Local-Token`。
2. **桥接层（preload）**：在 `contextIsolation` 开启、`nodeIntegration` 关闭、`sandbox` 开启的安全基线下，仅暴露文件选择、保存与令牌注入等白名单能力。
3. **主进程（Main）**：负责窗口与菜单、后端 Java 进程编排（spawn / tree-kill / 遮罩 / 崩溃自愈 / 优雅停机）、残留端口回收与数据目录注入。
4. **后端服务层（Spring Boot）**：分为 Controller（参数校验与转发）、Service（ai 续写 / quick / outline / inspire、check 自检、document 文档与版本导出、template 模板、material 素材）、ModelRouter（唯一大模型出入口）与 persistence（MyBatis-Plus 四表映射）。
5. **模型与数据层**：LOCAL 模式经 Spring AI 调用本机 Ollama（127.0.0.1:11434）；USER\_PROVIDED\_API 模式以 WebClient 直连第三方 OpenAI 兼容接口；持久化落于应用数据目录下的 `writer.db`（四表：document / doc\_version / prompt\_template / material）。

### 5.3 双模式模型调用流程

- **LOCAL 模式**：渲染进程发起续写 / 快捷处理请求 → 后端 Service 组装提示词 → ModelRouter 经 Spring AI 调用本机 Ollama → Flux 流式返回 → 由 SseEmitter 逐块下发 token 事件 → 前端流式插入正文。

- **USER\_PROVIDED\_API 模式**：用户在设置页填入服务商 / `apiKey` / `baseUrl` / `modelName`，配置仅存前端 localStorage；调用时密钥随 **POST 请求体**传入，后端以局部临时变量持有、请求结束即释放，**不落库、不落日志、不经 HTTP 头传输**；ModelRouter 以 WebClient 直连第三方 OpenAI 兼容接口并做 SSE 流式透传。

- **健康检测**：`/api/status/local-model` 探测 Ollama 服务与对话模型，返回三状态（UNAVAILABLE 服务不可达 / MODEL\_MISSING 服务连通但模型未下载 / READY 就绪），并给出推荐模型与 `ollama pull` 命令，本地不可用时前端置灰并引导。

### 5.4 桌面交付与进程编排流程

应用启动时，主进程先检测并回收残留 8080 端口，随后以 `--writer.data-dir=<userData>/data` 参数用 jlink 裁剪 JRE 拉起后端 jar；窗口先显示启动遮罩并轮询健康接口，就绪后才显示编辑器；运行中若后端进程异常退出则判定崩溃并自动重启；应用退出时优先调用仅回环可访问的 shutdown 端点，失败再以 tree-kill 强杀进程树，确保无残留、端口释放。

### 5.5 关键工程规范要点

- **安全红线**：`apiKey` 仅单次请求内存、日志全局脱敏（`sk-*`、`tvly-*` 等特征串替换为 `***`）、响应 DTO 不回显密钥；素材 / 模板内容不作为指令解析执行（防提示注入）。

- **数据红线**：事务内禁止包裹网络 IO / AI 调用 / 流式生成；文档删除采用事务级联；`doc_version` 以 `content_hash`（SHA-256）去重，回滚作为新版本追加不覆写。

- **配置规范**：提示词与自检词库外部化至 `agent.yml`，启动加载 + 设置页手动"重载配置"，不做文件监听热加载；配置解析失败回滚旧配置、服务不崩溃。

## 六、可行性分析

### 6.1 技术可行性

所选技术栈均为成熟且文档完善的开源方案：Electron、Vue3、TipTap、Spring Boot、Spring AI、SQLite、Apache POI 均有官方文档与活跃社区；Spring AI 1.0.0 GA 已正式发布，Ollama 接口稳定且兼容性良好。各关键工程难点（进程编排、SSE 资源释放、SQLite 并发、令牌鉴权、路径注入）均有明确的实现路径与规范约束，技术风险可控。

### 6.2 经济可行性

全部依赖均为开源免费软件，无需购买商业授权；开发工具（IDEA、VS Code、Node.js、Maven）均为免费；本地模式使用开源预训练模型，自有 API 模式的费用由用户自行承担且可自主选择。项目不含云服务器与商业数据库等持续性支出。

### 6.3 时间可行性

项目周期为 8 周（56 天），按"写作核心（W1–W4）→ AI 赋能（W3–W7）→ 交付（W8）"三阶段推进，共设 8 个里程碑（M1–M8）与对应 Git Tag（v0.1–v1.0）。业余开发每日投入 1–2 小时、周末集中验收与文档，并预留 +1 周弹性缓冲窗口，进度可控。

### 6.4 风险与对策

| 风险                       | 影响         | 对策                                      |
| ------------------------ | ---------- | --------------------------------------- |
| API 密钥泄露                 | 产生非预期费用    | 密钥仅请求体传入、单次内存、全局日志脱敏、响应不回显              |
| Ollama 不可用 / 模型缺失 / 认知偏差 | 用户误以为产品不可用 | 三状态健康检测、不可用置灰引导、FAQ 明确"只下载预训练模型，不需训练模型" |
| 提示词工程质量不稳定               | AI 体验欠佳    | 提示词外部化至 `agent.yml`、解析容错、LLM 结果优雅降级     |
| 编辑器偏移映射错位 / 大文档卡顿        | 标红定位不准     | 复用 ProseMirror 位置映射、替换走事务、编辑即清标记        |
| 数据结构并发写冲突 / WAL 膨胀       | 文档写入失败     | 单写连接池、统一 PRAGMA、事务红线、定期 checkpoint      |
| 打包后路径与进程残留               | 应用不可用      | 数据目录注入、jlink 交付、进程编排、打包后冒烟测试            |
| 外部依赖（联网素材）不确定            | 联网功能不可用    | 抽象 SearchProvider、未配置置灰、列入 P2 不阻塞交付     |

1. **可交付软件成品**：Windows x64 桌面安装包（NSIS 安装程序 + 免安装 zip），内含 jlink 裁剪 JRE 与后端 jar，安装即用；支持"本地 Ollama 离线模式"与"自有 API 联网模式"两条使用路径。
