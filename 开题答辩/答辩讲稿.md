## 一、开场与封面（P1｜约 40 秒）

各位老师好！我叫＿＿＿＿，我的毕业设计课题是《基于 Spring Boot 与 Spring AI 的桌面智能写作助手（码字工具）设计与实现》，指导教师是＿＿＿＿老师。

先用一句话概括我的选题：我要做的是一款面向个人创作者的 Windows 桌面写作工具，产品本体是"码字工具"，也就是编辑器、文档管理、防丢稿、版本和导出；AI 是写作过程中的赋能，而不是替代写作的自动化流水线。后端核心采用 Spring Boot 3.5.3 加 Spring AI 1.0.0，前端用 Electron 加 Vue3，正文编辑器用 TipTap，本地数据用 SQLite，最终交付一个 Windows x64 的桌面安装包。

下面我从背景、现状、目标、关键技术、技术路线、可行性和进度几个方面向各位老师汇报。

## 二、选题背景与痛点（P2｜约 60 秒）

首先是选题背景。大语言模型成熟之后，内容创作的效率被显著改变，网文、自媒体、公文这些长文写作场景，对 AI 辅助的需求非常旺盛。同时，开源模型加上本地推理工具 Ollama，让"模型在本机、数据不出本机"变成了现实；而 Spring 官方的 Spring AI 在 1.0.0 GA 之后，把模型抽象和流式输出统一了起来，让 Java 后端接入大模型的门槛明显降低。

但是现实里存在四个比较明显的痛点：第一，主流在线 AI 写作工具强依赖联网、正文要上传云端，隐私风险和断网不可用的问题都很突出；第二，这类工具往往重"一键成文"、轻"写作体验"，防丢稿、版本管理、多格式导出这些创作者的刚需反而被弱化；第三，本地模型使用门槛高，用户很容易把"下载预训练模型"误解成"要训练模型"；第四，Java 和 Spring 技术栈在桌面 AI 写作这个交叉场景里，缺少端到端的工程范例。

基于这些，我做了一个核心取舍：不做多 Agent 自动化流水线，聚焦"写得顺手的工具"加上"随手可用的 AI"。

## 三、研究意义（P3｜约 35 秒）

研究意义有三点。应用价值上，为个人创作者提供一个写作体验优先、隐私可离线的桌面工具，并且通过双模式兼顾离线隐私和开箱即用。技术价值上，以 Spring Boot 和 Spring AI 为核心，去实践桌面进程编排、SSE 流式资源释放、本机接口纵深防御、SQLite 并发这些真实的工程难点。方法论价值上，则是体现"工具本体为主、AI 为赋能"的产品取舍，并用里程碑驱动的方式，在有限的业余工时下保证毕设质量。

## 四、国内外研究现状（P4｜约 50 秒）

从研究现状看，已有方案主要分四类：一是 Notion AI、Jasper、秘塔写作猫、语雀 AI 这类 AI 写作工具，能力完善，但基本是云端 SaaS；二是以 Llama、Qwen 为代表的开源模型加 Ollama，让本地推理变得容易；三是 Electron 加 ProseMirror、TipTap 这样的桌面编辑器生态，已经证明本地优先的桌面写作工具有可行性；四是 Spring AI，模型抽象和流式能力都很成熟，但实践大多集中在服务端和云端。

综合起来，现有方案的空白也很清楚：离线与隐私能力弱、重生成轻体验、缺少 Java/Spring 栈的桌面端到端工程范式、本地模型环境缺乏标准化的可用性诊断。我的课题正好瞄准"桌面离线 + 数据隐私 + 写作体验与 AI 融合"这个交叉空白。

## 五、研究目标与主要内容（P5｜约 45 秒）

总体目标是：实现一款 Windows x64 桌面智能写作助手，以桌面码字工具为本体、AI 为写作赋能，通过 Spring Boot 3.5.3 加 Spring AI 1.0.0 统一接入本地 Ollama 和用户自有 API 两种模式，在 8 周内交付一个可安装、可运行、可演示的 MVP。

研究内容分四块：写作核心包括 TipTap 编辑器、文档管理、防丢稿、版本留存、多格式导出和舒适辅助；AI 赋能包括续写、快捷处理、大纲与灵感、素材收藏、全文自检和文体模板；模型接入是 ModelRouter 双模式加三状态健康检测；最后是桌面工程与交付，包括进程编排、本机接口安全、SQLite 并发和 Windows 打包交付。

## 六、系统总体架构（P6｜约 55 秒）

系统总体架构从上到下一共六层。最上面是渲染进程，用 Vue3 加 Element Plus 做界面，正文由 TipTap 承载，SSE 用 fetch 加 ReadableStream 处理。第二层是 preload 桥接层，在 contextIsolation 开启、nodeIntegration 关闭、sandbox 开启的安全基线下，只暴露文件选择、保存和令牌注入这些白名单能力。第三层是 Electron 主进程，负责窗口、后端 Java 进程的编排、启动遮罩、崩溃自愈、优雅停机和数据目录注入。

第四层是 Spring Boot 后端，分成 Controller、Service、ModelRouter 和 persistence，其中 ModelRouter 是唯一的大模型出入口。第五层是数据层，用 SQLite 单文件，四张表放在应用数据目录下的 writer.db。最下面是模型层，本地模式走本机 Ollama，自有 API 模式用 WebClient 直连第三方 OpenAI 兼容接口。

## 七、关键技术①：双模式模型接入（P7｜约 40 秒）

关键技术第一项是双模式模型接入。LOCAL 模式经 Spring AI 调用本机 Ollama，推理和文档全程留在本机；健康检测收敛成三个状态：UNAVAILABLE 服务不可达、MODEL_MISSING 服务连通但模型没下载、READY 就绪，不可用时前端置灰并给出引导。

USER_PROVIDED_API 模式让用户自备 OpenAI 兼容接口，后端用 WebClient 直连并做流式透传。这里有一条安全红线：密钥随 POST 请求体传入，只作为局部临时变量存在、请求结束就释放，不落库、不落日志、不经 HTTP 头传输、响应里也不回显。

## 八、关键技术②：桌面进程编排与交付（P8｜约 50 秒）

第二项是桌面进程编排与交付，这是能不能交付可用安装包的关键。主进程用 spawn 加 shell 为 false 的方式直接拉起后端，让 java 成为直接子进程，kill 才有效；再用 tree-kill，也就是 Windows 上的 taskkill /T /F，兜底杀掉整棵进程树。启动前回收残留的 8080，窗口先显示启动遮罩并轮询健康接口，后端异常退出就自动重启；退出时先调仅回环可访问的 shutdown 端点优雅停机，失败再强杀。

路径这块，主进程用 --writer.data-dir 把数据目录注入给后端，Java 侧按"启动参数、环境变量、user.home 兜底"的顺序解析，禁止写死相对路径。交付上用 jlink 裁剪 JRE 打进 extraResources，用户不用预装 JDK21，打包后还要做冒烟测试。

## 九、关键技术③：SSE 流式输出（P9｜约 40 秒）

第三项是 SSE 流式输出与资源释放。后端用 SseEmitter 承载，不引入 WebFlux；订阅 Spring AI 的 Flux 时持有 Disposable，客户端一断开就主动 dispose，终止对上游的调用。我们每 15 秒发一次心跳保活，心跳写失败就判定断连、立即释放，避免模型在后台空跑。前端统一用 fetch 加 ReadableStream，禁用 EventSource，用 AbortController 主动取消，事件严格限定为 token、error、complete 三种。

## 十、关键技术④：本机接口安全（P10｜约 40 秒）

第四项是本机接口安全。要强调的是，localhost 并不是安全边界，恶意网页可以通过 fetch 或者 DNS rebinding 访问本机服务。所以做了三重防御：第一，后端启动生成一次性随机令牌 X-Local-Token，写入应用数据目录的本地文件，由主进程读取后经 preload 注入渲染进程，令牌永远不经过 HTTP 传输，业务接口强制校验，不匹配返回 401；第二，Host 头只允许 localhost 和 127.0.0.1，防 DNS rebinding；第三，CORS 禁用通配符，只精确匹配 file:// 和开发环境的 localhost:5173。

## 十一、关键技术⑤：SQLite 与 offset 映射（P11｜约 40 秒）

第五项是 SQLite 并发和偏移映射。SQLite 是单写数据库，多连接写很容易 database locked，所以连接池最大连接数设为 1，连接初始化时统一设置 WAL、synchronous 为 NORMAL、busy_timeout 5000、foreign_keys 开启；同时立了一条红线：事务内禁止包裹网络 IO 和 AI 调用，也禁止长事务长读，再配合定时 checkpoint 防止 WAL 膨胀。

全文自检的偏移是以纯文本投影为基准的，需要映射到 ProseMirror 的文档位置才能标红和替换，我们复用 TipTap 的位置映射能力，替换走编辑器事务、进撤销栈。为了控制性能，标红只在用户手动点【全文自检】时触发一次，用户一旦编辑就清空标记，不做实时增量标红。

## 十二、功能模块一览（P12｜约 50 秒）

功能上分写作核心和 AI 赋能两块。写作核心有六大块：TipTap 编辑器、文档管理、防丢稿自动缓存、版本留存与回滚、txt/md/word 多格式导出，以及护眼暗色和悬浮字数统计。AI 赋能也有六项：光标续写、选中文字的扩写精简换风格调篇幅、大纲生成和灵感建议、素材收藏插入、全文自检，以及网文自媒体公文三套文体模板一键切换。

统一约定是：AI 调用都复用 ModelRouter，除自检外都流式返回，原地替换都可撤销可回退，不引入多 Agent 编排状态机。

## 十三、进度安排（P13｜约 45 秒）

进度是 8 周 56 天，分成 7 个阶段、对应 8 个里程碑和 v0.1 到 v1.0 的 Git 标签。W1 做环境和后端脚手架，跑通最小闭环；W2 做 Electron 桌面壳、编辑器和文档管理；W3 做 ModelRouter 双模式、续写和快捷处理；W4 做版本和导出，完成写作核心闭环；W5 做文体模板、大纲、灵感和素材；W6 做全文自检；W7 做舒适辅助、参数预设和联网素材；W8 做桌面打包交付、安全测试和文档。

因为是业余开发，每天投入 1 到 2 小时，周末集中做验收、集成测试和文档，并且整体预留了一周的弹性缓冲，每个阶段结束都会产出一个可以运行、可以演示的版本。

## 十四、预期成果与创新点（P14｜约 40 秒）

预期成果主要是：一个 Windows x64 桌面安装包，里面包含 jlink 裁剪的 JRE 和后端 jar，安装即用；一套含 v0.1 到 v1.0 标签的源码仓库；四份核心文档加 README、部署、排障、安全用例和 FAQ；以及一份覆盖全部功能点的演示录屏。

创新点和亮点主要有五个：写作本体加 AI 赋能的定位、双模式接入、桌面进程治理做到退出无残留、本机接口纵深防御让令牌不经过 HTTP，以及密钥零落盘。

## 十五、可行性分析（P15｜约 35 秒）

可行性方面，技术上所选技术栈都是成熟开源方案，文档完善、社区活跃，关键难点都有明确的实现路径；经济上依赖全部免费，没有商业授权和云服务器支出；时间上 8 周 8 个里程碑、每周验收加打标签，还预留了弹性窗口，并且有明确的 MVP 裁剪预案；风险上，密钥泄露、Ollama 不可用、偏移错位、路径失效这些主要风险，都分别有脱敏、三状态引导、位置映射加事务替换、数据目录注入加冒烟测试这些具体对策。

# 答辩问答预案

> 以下为评委可能提出的 10 个问题及标准回答要点，按重要性排序，建议熟记要点而非逐字背诵。

## Q1. 为什么用 Electron + Spring Boot，而不是纯 Web 应用或纯 Node.js 后端？会不会显得技术堆叠冗余？

**答：** 这是由产品定位和选题核心共同决定的。第一，产品定位是**桌面单机工具**，需要"数据落在本机、离线可用、作为本地进程被编排"，纯 Web 应用做不到这一点，也没有桌面进程生命周期可控的能力。第二，选题核心要求体现 **Spring Boot + Spring AI**，这是本课题的技术立论点，Spring AI 提供了统一的模型抽象和流式能力，能自然对接 Ollama 和 OpenAI 兼容接口，Java 生态的分层与工程规范也更利于体现工程能力。第三，两层并不是冗余：Electron 负责界面与本地交互体验，Spring Boot 负责业务、模型路由、安全与持久化，两者通过本机回环接口解耦，职责清晰，也符合"桌面壳 + 本机后端"这一被广泛验证的架构（例如很多带本地服务的桌面产品）。选择独立后端而不是把逻辑全塞进 Electron 主进程，是为了让 AI 调用的密钥管控、SSE 资源释放、SQLite 事务这些工程点能被规范地落地。

## Q2. 为什么锁定 Spring AI 1.0.0，而不是更新的 2.0？

**答：** 主要原因是**版本基线兼容性**。Spring AI 2.0 GA 基于 Spring Boot 4，而本课题锁定的稳定基线是 Spring Boot 3.5.3 + JDK21；如果强行上 2.0，就要整体升到 Spring Boot 4，会带来大量依赖连带升级和不可预期的兼容风险，与"8 周交付 MVP"的目标不符。而 Spring AI 1.0.0 作为 GA 版本，已经完整提供了 ChatClient 抽象、流式 Flux 输出与 Ollama 接入能力，完全满足本项目需求。锁定版本是**工程上规避风险的理性选择**，也符合"依赖版本严格对齐、禁止随意升级"的规范。

## Q3. 为什么用 SQLite 而不用 MySQL？

**答：** 由场景决定。本项目是**桌面单机、单用户、无登录、无多租户**，数据层只需要"本机可靠落盘"，不需要网络数据库。SQLite 是单文件嵌入式数据库，零安装、零服务、无端口无口令，数据即本地文件，备份就是复制一个 .db 文件，这与"桌面工具"的形态高度一致，也把攻击面降到很小。反过来，MySQL 需要独立服务进程、连接管理、数据卷和备份脚本，对个人本地使用明显过重，还引入了"数据库服务没启动导致文档打不开"这种额外的故障面。当然 MySQL 的并发能力强，但本场景是单用户，SQLite 在 WAL 模式下读写不互斥，完全够用。我在论文里也说明：当未来演进到多用户或云同步时，MySQL 会是必要选项，届时按对照表平滑迁移即可。

## Q4. 本地模式为什么不打包大模型？需要训练模型吗？

**答：** 明确说：**应用不内置、不打包任何大模型，也不需要训练模型**。本地模式采用的是用户自行安装 Ollama、pull 官方已经**预训练完成**的开源模型（如 Qwen2.5 系列），本质上是"下载并使用现成模型做推理"，全程不涉及任何训练环节。之所以不打包模型，一是模型动辄几个 GB，打进安装包会让体积失控；二是不同用户硬件差异大，模型应由用户按内存和显卡自行选择；三是这样能保证安装包的轻量与合规。为了消除用户"下载模型等于训练模型"的误解，我专门做了三点：健康检测给出推荐模型和 pull 命令、FAQ 与 README 反复澄清、设置页文案明确说明。另外，不想折腾本地环境的用户，可以直接填入自有 API 密钥，开箱即用。

## Q5. 桌面端如何保证关闭应用后后端 Java 进程不残留？

**答：** 这是本项目交付的关键点，我把它列为关键问题 R1，从五方面保证。第一，**拉起方式**：主进程用 `spawn(java, {shell:false})` 直接拉起，不用 shell 包装，让 java 成为 Electron 的直接子进程，这样 `child.kill()` 才有效。第二，**杀进程树**：额外用 tree-kill（Windows 等价 `taskkill /T /F`）兜底，退出时杀掉整棵 Java 进程树。第三，**优雅停机**：JVM 注册 ShutdownHook，后端暴露仅允许 127.0.0.1 访问的 shutdown 端点，退出时优先调接口优雅停机，失败再强杀。第四，**崩溃自愈**：监听 `exit/close` 事件，非主动退出判定为崩溃并自动重启。第五，**残留端口回收**：启动前检测 8080，如果是上次残留进程就先回收再启动。最后，打包后会做冒烟测试，专门验证"退出无残留进程、8080 端口已释放"。

## Q6. 如何保证用户第三方 API-Key 的安全？

**答：** 我采用的是"全链路最小暴露"策略，主要有六条。第一，**唯一来源**：密钥只从 POST 请求体传入，不使用 HTTP 头传密钥。第二，**最短生命周期**：密钥在方法内只是局部临时变量，请求处理结束立即释放，绝不赋值给成员变量、不缓存、不落库。第三，**日志脱敏**：日志输出层做统一正则脱敏，把 `sk-*`、`tvly-*` 这类特征串替换成 `***`，作为最后一道防线，同时业务代码禁止打印包含密钥的入参对象。第四，**响应不回显**：响应 DTO 和异常报文都严禁回显密钥。第五，**前端约束**：密钥只存前端 localStorage、不上传后端，主进程和渲染进程禁止 console 打印。第六，**专项测试**：交付前执行密钥泄露专项测试，检查日志、异常堆栈和前端控制台都无明文密钥。

## Q7. SSE 为什么不用浏览器原生的 EventSource？

**答：** 主要有三个原因。第一，**EventSource 只支持 GET 请求**，而本项目的续写、快捷处理等接口需要携带上下文、文体、模型参数以及用户自备的 apiKey，这些必须通过 POST 请求体传递，EventSource 无法满足。第二，**EventSource 无法自定义请求头**，而本项目的业务接口需要携带 X-Local-Token 做本机接口鉴权，EventSource 也做不到。第三，**EventSource 的取消与错误重连控制较弱**，我们用 fetch + ReadableStream 可以配合 AbortController 精确控制取消，也便于统一处理断连与重连。因此规范里明确禁用 EventSource，全部用 fetch + ReadableStream。另外在后端，我用 SseEmitter 承载 Spring AI 的 Flux 并持有 Disposable，配合约 15 秒心跳保活，写失败就立即 dispose，保证客户端断开后上游模型调用被及时释放，不会在后台空跑。

## Q8. 全文自检标红为什么不做实时增量，只做手动触发一次？

**答：** 这是一个**性能与体验权衡后的主动决策**。实时的意义在于"输入即标注"，但代价是每次用户输入都要重新计算问题偏移、重建纯文本和 ProseMirror 文档位置的映射、刷新装饰（Decoration），在长文场景下重算成本很高，容易造成编辑卡顿，反而破坏写作体验。而且自检本身包含较重的规则引擎和 LLM 语义检查，不适合高频触发。所以 v1.0 的策略是：**仅当用户点击【全文自检】时执行一次校验并生成标记，用户一旦编辑输入就清空全部标记，需要时再点一次重建**。这样既保证了标红定位的准确性，又规避了高频重算的开销。这也是我列为关键问题 R5 的技术取舍。

## Q9. 你的工作量与进度如何保证？业余开发会不会延期？

**答：** 进度保障有四个机制。第一，**里程碑驱动**：8 周分成 7 个阶段、8 个里程碑，每个阶段结束对应一个 Git 标签（v0.1–v1.0），每个里程碑都要求产出可运行、可演示的版本，绝不堆积技术债到最后一周。第二，**周末固定验收**：工作日每天编码 1–2 小时，周末集中做阶段验收、集成测试和文档。第三，**弹性缓冲**：整体预留了一周的缓冲窗口，某阶段阻塞时优先整体后移。第四，**裁剪预案**：我提前列了明确的降级顺序，第一档是绝对禁止裁剪的核心闭环（编辑器加防丢稿、文档管理、续写、快捷处理、双模式与密钥安全、文体模板、大纲、全文自检规则引擎、版本与导出、进程编排、本机令牌鉴权），第二档是可后置到 P2 的次要功能（联网素材、语义级自检、打字机模式、自定义模板等），一旦某任务超出计划工时 50% 就触发降级，保证 8 周内核心 v1.0 一定交付。

## Q10. 这个课题的创新点和亮点是什么？相比现有工具有什么不同？

**答：** 我认为亮点主要体现在定位差异和工程实现两方面。定位上，我做的是"**写作本体 + AI 赋能**"——优先把编辑器体验、防丢稿、版本、导出这些写作本体做扎实，AI 作为随手可用、可撤销可回退的赋能，而不是"一键成文"的自动化流水线，这恰好补上了现有工具"重生成、轻体验"的不足。模式上，**双模式接入**同时满足两类用户：注重隐私的选择本地 Ollama 完全离线，不想折腾的直接填自有 API 密钥开箱即用。工程上，我系统性解决了桌面 AI 应用的四个共性难题：桌面进程编排做到退出无残留（R1）、本机接口纵深防御让令牌不经过 HTTP（R3）、SSE 流式的资源释放与断连保活（R4）、以及 SQLite 单写并发下的一致性与事务红线（R2）。这些实现不仅有功能价值，也形成了一套可复用的工程经验，这也是本课题区别于普通"调个模型 API"类实现的核心竞争力。
